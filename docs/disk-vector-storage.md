# Bounded native vector storage (v4.3.14 candidate)

The embedded Qdrant client retains all dense vectors, payloads and point IDs in the service process. Persisting its SQLite files does not bound that RAM. This profile replaces only that dense vector storage with an indexed SQLite store: 2 MiB connection cache, no mmap, disk temporary tables, 128-vector scoring batches and at most 400 candidates (the pinned Mem0 four-times over-fetch for API TopK100). No corpus-size cache is kept across requests.

Pinned Mem0, original sources, embedding calls, user scopes, selector prompt, 32/8/8 candidate/image/selection limits, context packing, budgets and retry ownership remain unchanged. The pinned Qdrant filter evaluator and cosine calculation are reused. This is a storage implementation change, not byte-identical Qdrant: normalized float32 scores are checked to 1e-6 and exact-score ties use descending ID instead of numpy's unspecified tie order. Sparse vectors and unsupported operations fail closed. The deployed dense profile has no fastembed model.

Migration reads only trusted locally generated Qdrant persistence after stopping its writer. It streams newest-ID records into a new database and verifies every ID, normalized vector and complete payload in a second pass. It does not modify the source, source archive, history, accounting or provider journals, and cannot overwrite a partial target. Existing state refuses startup without a verified migration marker. Preserve the old database; after new writes, reverting to it requires reconciling those writes, not merely changing the image.

Validation uses synthetic data only: reference Qdrant Top400 search/filter comparison, atomic rollback, user isolation, whole migration and source immutability, Mem0 restart/idempotence, and existing native parallel/failure cases. A 700000-point synthetic storage pressure run uses 3000 payload bytes per point; it is a storage RSS experiment, not a complete Full run. No official question, protected payload, gold, model credential or provider response is published here. Disk storage still grows with the corpus; disk capacity and per-request memory require separate operational monitoring. This change does not claim an official score or prove all possible OOM causes are eliminated.
